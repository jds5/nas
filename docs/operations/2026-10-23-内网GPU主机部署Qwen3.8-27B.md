# 内网 GPU 主机部署 Qwen3.8-27B

时间：2026-10-22 23:40 – 10-23 01:20。目标主机 `192.168.50.20`（`yao-home`，Windows 11，RTX 5080 16 GB，Ryzen 7 9700X，32 GB 内存），不是 NAS。NAS 经已授权的 SSH 密钥以 `yaoch` 登录操作；NAS 本身无改动。

## 选型

| 项目 | 选择与理由 |
| --- | --- |
| 模型 | `byteshape/Qwen3.8-27B-GGUF` 的 `Qwen3.8-27B-IQ4_XS-3.84bpw.gguf`（版本 `3fdfbd9b`，13,083,052,416 字节，SHA-256 `89434f23…f218b78b` 已核对）。逐张量学习量化格式的 4-bit 级 GGUF，是 4-bit 档中显存占用最低的；AWQ/GPTQ 等严格 INT4 需 15–17 GB，放不进约 14 GB 空闲显存 |
| 模型结构 | 64 层中 48 层线性注意力、16 层全注意力（4 个 KV 头 × 256），q8_0 KV 约 32 KiB/token；GGUF 内含 MTP 头，可做投机解码 |
| 推理 | llama.cpp 官方镜像 `ghcr.io/ggml-org/llama.cpp:server-cuda13@sha256:dfe42bda…63e2977`（build 11804）。CUDA 13 版带 Blackwell（sm_120）原生内核；CUDA 12 版按 12.4 编译，只能兼容运行，故按用户要求升级驱动而非换镜像 |
| 驱动 | 原 610.88（CUDA 13.3）不满足镜像 `cuda>=13.4`；用户自行升级到 621.01（CUDA 13.5）并重启 |

## 部署

- 文件：`C:\llm\qwen38\compose.yaml`（服务 `qwen38-27b`，`restart: unless-stopped`，`gpus: all`）；模型在 Docker 外部卷 `llm-models`（加载 12 GB 约 5 秒，比挂载 Windows 目录快）。
- 参数：`-c 16384 -fitt 512 -np 1 -fa on -ctk q8_0 -ctv q8_0 --no-mmproj --spec-type draft-mtp --spec-draft-n-max 2`，默认采样为官方思考模式推荐值 `temp 1.0 / top_p 0.95 / top_k 20 / min_p 0`，客户端可按请求覆盖（非思考模式官方建议 `temp 0.7 / top_p 0.8 / presence_penalty 1.5`，并传 `chat_template_kwargs.enable_thinking=false`）。
- 访问：仅 `127.0.0.1:8080`（OpenAI 兼容 `/v1/chat/completions`，模型名 `qwen3.8-27b`，网页界面 `http://127.0.0.1:8080/`），无 API 密钥，未开放局域网、未改 Windows 防火墙。
- SSH 会话中 Windows 凭据助手不可用（`A specified logon session does not exist`），另建 `C:\llm\qwen38\docker-config`（空配置，仅拉公开镜像）并在执行时将凭据助手移出 PATH；不影响 Docker Desktop 原登录信息。
- 用户重启后 Docker Desktop 未自动启动，助手用一次性计划任务在用户已登录的桌面会话中启动了它（任务执行后已删除）。

## 注意与回滚

- 显存余量小：桌面程序（浏览器、微信等）显存增长或运行游戏时可能变慢或抢占显存；需要显卡时 `docker compose -f C:\llm\qwen38\compose.yaml stop`，用完再 `start`。
- 随开机运行依赖 Docker Desktop 自启：其设置 `AutoStart` 为 false（注册表 Run 项存在但本次重启未拉起），未擅自修改；如需开机自动提供服务，在 Docker Desktop 设置中开启 “Start Docker Desktop when you sign in”。
- 开放局域网访问需另行决定：改端口绑定、加 `--api-key`、添加仅限 `192.168.50.0/24` 的防火墙规则。
- 回滚 / 卸载：`docker compose -f C:\llm\qwen38\compose.yaml down`；删除模型 `docker volume rm llm-models`（约 12.2 GiB，需确认后执行）；删除 `C:\llm\qwen38`。驱动升级由用户执行，不在回滚范围。
- 未验证：长上下文（接近 16K）下的速度与显存、并发请求、局域网访问。

## 追加：面向 Agent 的长上下文（同日）

用户计划用于 Agent，单人使用，可接受较慢输出。结论与依据：

- **上下文下限**：Agent 框架的系统提示与工具定义通常占 1–2.5 万 token，Qwen3.8 默认保留历史思考内容，读几个文件就会超过 32K。实用下限 64K，建议 128K；官方 Agent 评测均使用 256K。
- **KV 量化**：社区 KL 散度测试显示 q8_0 K/V 几乎无损，Qwen 系列 q4_0 的误差集中在长文档与工具调用（[localbench](https://localbench.substack.com/p/kv-cache-quantization-benchmark)、[llama.cpp #23470](https://github.com/ggml-org/llama.cpp/discussions/23470)），故保持 q8_0，不用 q4_0。

现场测试（中段插入暗号的仓库文本，开启 MTP 2；显存为启动后读数）：

| 配置 | 显存剩余 | 30.5K 输入 | 83.6K 输入 |
| --- | --- | --- | --- |
| 64K，自动把整层放 CPU | 0.44 GB | 预填 1345 tok/s，生成 9.1 | — |
| 64K，12 层 FFN 放 CPU（`--n-cpu-ffn 12`） | 0.44 GB | 1346 / 18.3 | — |
| 64K，KV 放内存（`-nkvo`） | 1.5 GB | 1142 / 10.5 | — |
| 128K，26 层 FFN 放 CPU，q8/q5_1 | 0.17 GB（过紧） | 1053 / 8.1 | 862 / 7.8 |
| **128K，KV 放内存（采用）** | **1.2–1.4 GB** | **1122–1134 / 9.7–10.9** | **876 / 6.2** |
| 128K，KV 放内存，关闭 MTP | 2.0 GB | 1402 / 7.6 | 1056 / 4.1 |
| 256K，KV 放内存 | 0.4 GB | — | 797 / 6.1 |

所有配置暗号检索均正确。采用 128K＋`-nkvo`：权重全在 GPU，q8_0 KV（约 4.3 GiB）在内存，显存余量最大；短对话生成约 26–27 tok/s，随上下文加深降至 6–11 tok/s；服务端默认在内存缓存提示前缀，Agent 多轮对话只需预填新增部分。工具调用（OpenAI `tools`）实测返回正确的 `tool_calls`。

- 加载改为 `--load-mode dio`（本版本已无 `--no-mmap`），避免 12 GiB 模型文件留在 WSL 页缓存；清理测试遗留缓存后 WSL 占用由 19.3 GB 降至 8 GB，Windows 可用内存约 10 GB。
- 快速模式（16K、全 GPU、66–100 tok/s）保存为 `C:\llm\qwen38\compose-16k-fast.yaml`，切换：`docker compose -f <文件> up -d`（两文件为同一项目，后启动者替换前者）。
- 进一步扩大上下文的最大收益是把显示器接到主板（9700X 核显）输出，让独显不承担桌面（当前约 1.4–1.8 GB），可在全 GPU 下开到约 64K；需用户自行操作，未验证。
- 未验证：256K 实际满载、长时间 Agent 会话中的内存增长、WSL 自动回收内存行为。
