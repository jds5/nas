# 网页终端断连排查与优化（2026-10-07）

## 现象与证据

用户反馈发送指令约 5 秒后断开，Windows 焦点仍在页面；另一次返回页面发现已断开。此前 0.5.1 已部署固定 24 小时连接期限。

现场检查 web、SSH 转接与 NPM 均无容器重启；web 无 OOM，cgroup memory/pids 事件无资源耗尽记录。生产文件与 0.5.1 一致，24 小时上限生效。NPM 读空闲超时 1000 秒，不存在已发现的 5 秒空闲关闭配置。窗口失焦本身没有断开逻辑。

旧版本没有连接关闭原因日志，无法将这两次断开准确归因于网络、代理、输出拥塞或协议错误，也不能据此证明 Cloudflare 是故障来源。排查发现两个可改进点：

- 原输出流控累计超过 1 MiB 或 socket 缓冲超过 512 KiB 会直接关闭；隔离测试注入约 1.8 MiB 中文/emoji 输出块，旧版确定关闭，新版无截断完成。真实 PTY 通常分块较小，这个测试证明边界薄弱，**不是两次现场故障的复现**。
- 原心跳只有协议 Ping/Pong，没有穿过完整代理链的应用消息确认；异常关闭时页面也没有代码、原因或有限恢复机制。

## 0.5.2 变更

- 保留协议 Ping/Pong，浏览器与服务端每 15 秒双向应用心跳；服务端 90 秒没有 Pong 或有效应用消息、浏览器 120 秒没有服务端消息才关闭。恢复网络、焦点或可见性时立即探测。心跳不作为终端输入。
- 输出分块保留 Unicode 字符边界，待确认窗口最多 128 KiB，暂停/恢复 PTY 控制输出速度；待发送加待确认总计超过 4 MiB 才关闭。浏览器短时渲染变慢不直接关闭。
- tmux 异常代码 1006/1012/1013/4000 可自动重试三次，延迟 1/3/8 秒。每次重新鉴权、获取单次票据及校验原会话身份；保留原截止时间，不重跑 Codex、不新建 tmux、不重发指令。临时 SSH、主动断开、24 小时到期、协议错误不自动重连。等待时可以取消。
- 图片提交结果不确定时保留草稿并提示先核对。恢复时终端设备查询仍正常应答，这不是重放用户输入。
- 页面显示关闭代码及随机连接编号；结构化日志只记录连接生命周期、内部原因和数值指标，不记录命令、输出、身份、会话名或凭据。原每身份/全局连接配额与 Access 保护不变。

24 小时是服务端关闭上限，不是对网络绝不断线的保证。自动重连保持正常客户端的原期限；持有有效 JWT 的用户仍可手动新建一个最长 24 小时的连接。JWT 过期不终止已建连接，但不能凭旧 JWT 重连。

## 下次断连定位

先记录页面的关闭代码、编号和发生时间；可在 NAS 查询最近事件：

```bash
docker logs --since 30m nas_web_terminal 2>&1 | rg 'terminal_(opened|closed)'
```

| 代码 / 日志原因 | 含义与处理 |
| --- | --- |
| 1006 / peer_closed | 未完成关闭握手，网络或代理中断；结合编号和时间查链路，tmux 自动恢复 |
| 4000 / heartbeat_timeout | 一段时间没有收到心跳/有效消息；关注 pongAgeMs、activityAgeMs |
| 4001 / session_expired | 到固定期限，手动重新登录/连接 |
| 4001 / session_unavailable | 会话身份变化，刷新列表重新选择 |
| 4002 / output_overflow | 有界输出队列仍溢出，检查缓冲指标，不盲目无限增大 |
| 1008 / invalid_ack、invalid_message | 协议/确认异常，记录代码和编号后排查 |
| 1000 / terminal_exit | 终端 client 退出，结合 exitCode/signal 查看 tmux/SSH 状态 |

peer_closed 表示应用观察到对端关闭，不等于确认用户主动关闭。客户端发现心跳超时发起 4000 时，服务端会记 peer_closed；前后端通过代码和编号关联。服务端不记录原始对端 reason。
