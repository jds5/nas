# NAS 运维巡检任务说明

用户说“执行运维”“做一次巡检”或类似指令时，按本说明完成一次巡检并汇报。本说明是常设流程，每次巡检的结果另写带日期的记录。方法沿用 [10-22 攻击日志检查](2026-10-22-NAS巡检与外部攻击日志检查.md)、[10-23 升级巡检](2026-10-23-NAS服务升级巡检.md)和 [10-24 服务升级](2026-10-24-NAS服务升级.md)。

## 原则

- **巡检阶段只读**：不升级、不重启、不改配置、不删数据、不改防火墙或端口。会改变状态的探测（例如唤醒休眠磁盘、触发应用初始化）也要避免。
- **先汇报，后升级**：汇报中给出“推荐升级”和“全量升级”两个选项，由用户选择，**选定后才执行**。用户没选之前不拉镜像、不升级。
- 历史记录只作基线，以现场为准；数据从现场读取，官方版本从实时来源读取（GitHub API 排除预发布、官方安全通告、发行版仓库），不用搜索摘要或缓存代替。
- 需要 sudo 或 root 才能做的检查，先说明需要什么权限；拿不到权限时，在汇报里列为“未检查”，不能写成“正常”。
- 比较时间范围：默认从上一次巡检记录之后开始，至少覆盖最近 14 天。

## 一、安全：是否被攻击或入侵

| 检查项 | 做法 | 判为异常的情况 |
| --- | --- | --- |
| SSH | `journalctl` 读 ssh 认证日志；核对 `sshd_config` 仍为仅密钥登录；核对 `~/.ssh/authorized_keys` 的数量、指纹和修改时间 | 有密码登录成功；出现未登记的密钥；针对真实用户 `yao` 的大量失败尝试；登录来源不像本人（境外、非常用运营商段） |
| 账号与提权 | `/etc/passwd`、`shadow`、`group` 的修改时间；能登录 shell 的账号；sudo 日志 | 出现新账号；文件被改动；出现不明 sudo 命令 |
| 公网 Web（NPM） | `/opt/nas/npm/data/logs/` 下的访问日志和 fallback 日志：统计敏感路径探测及其返回码，检查 `origin-home` 的来源是否全部是 Cloudflare 地址段 | 敏感路径（`.env`、凭据、管理接口）返回 2xx；有请求绕过 Cloudflare 直连源站；单个来源访问量突增 |
| 应用登录 | Immich、Jellyfin、Navidrome、Kavita、网页终端，以及 Access 保护的应用（例如 Homeland 的 `[access-denied]` 日志） | 集中出现登录失败；陌生来源登录成功 |
| 防火墙与内核 | 内核日志里的 UFW 阻断记录；读取 UFW 规则需要 root | 短时间大量阻断；规则被改动 |
| 端口暴露 | 现场 TCP/UDP、IPv4/IPv6 的监听情况，与[服务与端口清单](服务与端口清单.md)逐项对照 | 有未登记的监听；管理端口监听在 `0.0.0.0` 或 `[::]`，而且能从公网访问 |
| 持久化痕迹 | 用户 crontab 和系统 crontab、systemd 单元和定时器、新出现的容器或镜像 | 出现不在记录里的定时任务、服务或容器 |

结论要区分三种情况：“有扫描或尝试，都被拒绝”；“发现入侵迹象”；“因权限不足未能核实”。发现入侵迹象时立即单独汇报，并停止后续升级建议；不得擅自清理，以免破坏证据。

## 二、主机、服务与定时任务

| 检查项 | 做法与标准 |
| --- | --- |
| 主机 | 运行时长、负载、内存和 Swap（与上次对比）、CPU 和 NVMe 温度 |
| 存储 | 各盘的空间和 inode 用量；SMART：只查已经在转的盘，**不唤醒休眠的 sda、sdb**（见[备份盘休眠](备份盘休眠.md)）；NVMe 错误日志计数与上次对比 |
| 内核 | I/O、EXT4、NVMe、ATA 错误；OOM（记录被杀进程所属的容器） |
| systemd | 系统级和用户级的失败单元都应为 0；定时器的上次运行时间要正常 |
| 容器 | 是否运行、健康状态、重启次数；停止的容器只能是已登记的那几个（目前是 `homeland_xhs_qr_publisher`、`stock_scheduler`）；查看各容器近期日志里的错误 |
| 定时任务 | 用户 crontab：`git-backup.sh`（04:00）、磁盘休眠脚本、stock watchdog 等，看最近一次执行结果；Stock 的采集和研究任务是否按时跑 |
| 备份链 | restic 主备份、配置 Git 备份推送、第二备份盘镜像、OneDrive 异地同步：每一环都要找到**最近一次成功的日志**，并写明是哪一天。只看到“已执行”不算成功 |
| 入口 | 各公网域名的返回码与上次一致；内网服务健康接口正常 |
| 遗留项 | 上次记录的“需要关注”逐项复查，状态变了的要写明 |

## 三、软件与服务版本

1. **宿主机**：`apt list --upgradable`，分开列出 Debian 主仓库、安全仓库和 Docker 仓库的待更新包。要写明软件包索引是什么时候更新的：刷新索引需要 sudo，没刷新时如实说明。
2. **容器服务**：读取每个运行容器的镜像引用和版本标签，以及应用实际报告的版本，与官方最新稳定版对比。使用滚动标签（如 `stable`、`pg16`）的镜像，比较远端 linux/amd64 的镜像层；LinuxServer 镜像要同时比较应用版本和构建号。
3. **自建项目**（Stock、Homeland、DDNS-CF-Go、网页终端、OpenList 自建镜像等）：检查基础镜像（node、nginx、python、playwright）是否有安全更新。
4. **生命周期**：数据库和运行时的停止支持日期，例如 PostgreSQL 14 将于 2026-11-12 停止支持。
5. **宿主机 CLI 工具**：Claude Code 等，只汇报，不自动更新。Codex CLI 按用户要求（2026-10-30）不再检查、不再汇报。
6. 对每个候选，阅读 release notes 和安全通告（GHSA、nginx.org、Debian DSA、CISA KEV），记录 CVE 编号与严重程度，并**判断是否影响本机**：用到的功能是否受影响、服务是否暴露在公网。

## 四、升级分级

| 分级 | 归入条件 |
| --- | --- |
| **推荐升级** | ①严重或高危 CVE，或已有在野利用，而且本机用到了受影响的功能；②公网可访问的服务（NPM、Immich、Jellyfin、网页终端、SSH、Cloudflare 相关组件等）的安全修复；③重大更新：主版本或重要次版本更新、修复数据损坏或丢失的问题、上游要求尽快升级；④即将或已经停止支持的组件；⑤宿主机安全仓库的更新 |
| **全量升级** | 推荐升级的全部内容，**再加上**：不关键的补丁版本、只在内网使用且风险低的修复、LinuxServer 构建号更新、滚动标签的镜像重建、依赖更新、宿主机非安全包、不影响本机的 CVE 修复 |

- 只在全量升级时才更新的项目：不关键的小版本、小更新。
- 无法判断时，按“严重程度 × 暴露面”判断：同一个 CVE，公网服务归入推荐，纯内网服务可以归入全量，但要写明理由。
- 重大更新（跨主版本、数据库迁移）即使归入推荐，也要单独写出风险、迁移步骤和停机时间。如果需要另外安排维护窗口，要明确说出来。
- 不能升级或暂缓的项目也要列出原因：上游没有修复版、需要 sudo、有任务正在进行等。

## 五、汇报格式

先在对话中汇报，然后写成 `docs/operations/YYYY-MM-DD-NAS巡检.md`，并更新 README 导航，最后提交并推送。

```markdown
## 结论（3–5 条：是否被攻击、服务是否正常、最大风险、建议哪个升级选项）
## 安全（SSH / Web / 应用 / 防火墙 / 端口 / 持久化）
## 主机与服务（异常在前，正常的汇总写）
## 升级选项
### 选项 A：推荐升级（N 项）  表格：项目 | 当前 → 目标 | 理由（CVE、严重程度、是否暴露） | 停机与风险
### 选项 B：全量升级（A + M 项）  只列出 A 以外新增的项目
### 暂缓 / 无法升级
## 需要用户处理或授权（sudo、维护窗口、云端配额等）
## 未检查 / 未验证
```

## 六、用户选定后执行升级

- 每个容器升级前都备份：`inspect.json`、Compose 原文、停止后导出的数据（附 SHA-256），旧镜像打标签保留为 `nas-rollback/<容器名>:upgrade-YYYYMMDD`。数据库要先做逻辑备份，并在隔离容器里恢复验证，然后再升级。备份目录放在 `/home/yao/.nas-maintenance-backups/` 下，不进 Git。
- 升级后逐项验证：版本号、核心数据量与升级前一致、入口返回码不变；端口、挂载、网络、环境变量与升级前对比无意外变化。
- 宿主机 Docker 升级会重启全部容器，需要 sudo，要单独确认维护窗口。
- 正在进行的任务（下载、抓取、转码）要等完成后再升级对应服务，或者先征得用户同意。
- 执行结果另写 `YYYY-MM-DD-NAS服务升级.md`，写明版本、验证结果、回滚方法和未完成项；更新[服务与端口清单](服务与端口清单.md)与 README；提交 `nas-config` 等相关仓库。
