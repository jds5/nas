# Immich 视频上传慢、易中断：只读排查

日期：2026-09-29。反馈来自约一个月前某位手机用户；照片上传正常，视频慢或失败。未取得当时的手机日志、视频大小、前后台状态及准确时间，不能定案。

## 当前现场证据

- Immich Server、PostgreSQL、Machine Learning、Redis 均运行且健康。Server 自 9 月 23 日本轮启动以来 RestartCount=0、OOMKilled=false；不能由此排除一个月前的问题。
- 实际 NPM Host 4 为 `immich.rokano.org`，转发 `immich_server:2283`，无公网 2283 映射。NAS 本地经证书校验的 HTTPS 8443 请求 `/api/server/ping` 返回 pong。
- 当前 DNS 解析到单个公网 IPv4，没有 AAAA；未核实反馈用户当时实际走的域名/端口及代理链，不能用当前 DNS 反推历史路径。
- 已生效配置：`client_max_body_size 50000M`、`proxy_request_buffering off`、`proxy_read_timeout 600s`、`proxy_send_timeout 600s`，HTTP/1.1。普通视频不应触发当前 NPM 的大小上限，也没有“先完整缓存上传再发给 Immich”的配置。
- 未发现设置 `client_body_buffer_size` 或 `client_body_timeout`。按 Nginx 默认行为，前者为 8K/16K（平台相关），后者 60s。官方 Immich 示例建议 body buffer 1024k；属于可考虑的吞吐优化，不是本次已确认根因。client_body_timeout 衡量两次读取之间无数据的间隔，不能说成“总上传超过一分钟必失败”。
- 照片数据盘剩余约 6.5 TB；系统盘剩余约 1.4 TB；可用内存约 20 GiB，采样时服务 CPU 很低。未发现当前容量紧张；没有做磁盘/公网吞吐压测，不能排除历史忙碌或外网带宽问题。

## 原因判断

1. **优先复现手机前后台与网络问题**：大视频占用时间长，更容易遇到锁屏、省电限制、Wi-Fi/蜂窝切换或不稳定网络；Immich 官方明确前台与后台备份是独立机制，后台执行受操作系统调度。照片成功只能证明基本连接与认证可用。
2. **确认历史入口是否经过额外代理**：如果当时走 Cloudflare 代理或其他中转，照片可成功而较大视频遇到边缘大小/超时上限；当前 NPM 50 GB 不能覆盖上游限制。尚未取得当时入口证据，不把 Cloudflare 判为根因。
3. **区分视频准备、实际传输与后处理**：若 iPhone 使用优化存储，视频可能先从 iCloud 拉到本地；若仅个别视频在 100% 后失败，需对照客户端错误和相应资产元数据任务，不能一律称为上传带宽问题。
4. **代理参数仅列为优化候选**：可考虑按官方示例增加 1024k body buffer；只有确认读请求体长时间停顿时再讨论 client_body_timeout。盲目提高所有 timeout 无法修复手机进程被系统暂停、边缘硬上限或线路丢包。

## 最小复现方案（尚未执行）

由用户选一个曾失败或相近大小的视频，保持 Immich 在前台、屏幕常亮，先稳定 Wi-Fi，再另换网络对照；记录文件大小、开始/失败时间、进度是否卡在 0%/中途/100%、手机系统和 App 版本。首次成功后同文件可能被去重跳过，后续对比不能把去重当上传测速，应使用尚未上传的相近大小样本，避免删除已备份资料。

再在同一网络用浏览器上传另一份相近大小样本：浏览器成功而手机失败时偏向 App/后台/文件准备问题；两者相近阈值失败时重点检查网络、边缘限制和服务端日志。诊断只需客户端错误摘要，不提供密码、API key 或原始含令牌日志。确认失败时间后再对齐 NPM 与 Immich 日志，必要时先增加不记录 query/token 的上传耗时与字节数指标。

本次未修改配置、重启服务、上传或删除媒体，也未读取 .env。当前结论是排除若干常见配置问题，尚未定位历史根因。
