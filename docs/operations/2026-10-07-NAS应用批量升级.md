## 实施与备份

逐个停止目标服务，导出一致的应用配置和数据，再重建容器。未改动媒体库和下载文件。备份约 **10.44 GiB**，保留在私有目录：

```text
/home/yao/.nas-maintenance-backups/apps-upgrade-20261007/
```

其中有原始容器信息、原 Compose、各服务 `mount-*.tar`、备份 SHA256 清单、升级及验证结果。目录和敏感文件限制访问，未加入 Git。旧镜像均保留为 `nas-rollback/<容器名>:20261007`，本轮没有执行镜像清理。

镜像下载遇到链路缓慢，使用独立工具按范围下载公开 OCI 内容，校验 SHA256 后导入 Docker，未重启 Docker daemon。为下载临时添加的两条 Mihomo CDN 直连规则已撤销，生产代理配置恢复为原始字节内容。

Docker 导入过程产生的本地镜像摘要不能当作上游仓库摘要。最终 Compose 使用已向上游解析核对的 Linux amd64 manifest digest；逐个验证上游文件系统层和镜像启动配置与运行镜像一致。`upstream-pins.json` 保存对应关系。运行容器可能仍显示导入时的本地镜像引用；后续 Compose 重建会使用已固定的上游引用，并可能需要访问仓库。

生产配置位于 `/opt/nas` 对应服务的 `docker-compose.yml`，ARR 共用 `arr-stack/docker-compose.yml`。仅提交本轮 Compose 镜像变更；应用自行迁移产生的配置、运行状态及日志不混入提交。`ddns-go/` 原本被生产仓库整体忽略，其 Compose 已在现场更新并留有私有备份，未强制将该目录加入 Git。

## 回滚

升级后的数据库不应直接交给旧版应用。私有备份目录已准备单服务恢复脚本，依赖 Python 3、PyYAML、Docker/Compose 和相应目录权限。示例：

```bash
python3 /home/yao/.nas-maintenance-backups/apps-upgrade-20261007/rollback.py jellyfin
```

脚本先核对备份摘要和旧镜像，停止指定服务，将当前数据保留为 `.post-upgrade-时间戳`，恢复升级前数据及旧镜像，然后重新启动。只影响指定服务；新增的升级后数据不会合并回旧数据。Beszel 回滚需配套恢复 hub 和 agent。执行前仍需确认回滚目标和期间新增业务数据。

脚本已做语法检查，**本次未实际执行数据恢复演练**。恢复后必须重新验证页面、数据数量和相关业务链路。

## 遗留与使用提示

- Sonarr、Radarr、Prowlarr 新增 `AllowedHostsCheck` 告警，提示未配置允许的主机名；本轮保留原访问设置，未直接收紧而中断客户端。应单独核对内网地址、容器名称和反代 Host 后设置。
- 既有索引器长期不可用告警仍存在，本轮没有重配或删除索引器。
- Diun 对运行中的 `stock_report_share` 报本地镜像对象缺失，这是升级前已存在的状态；该应用未重建，需在其独立维护中处理。
- Dozzle 11 会重新建立登录会话，可能需要重新登录；旧 `DOZZLE_TAILSIZE` 环境变量被新版忽略，日志会提示该项，不影响服务启动。
- Byparr 3.x 的 `/health` 会启动浏览器访问 Google，不宜用几秒超时反复轮询。本轮改为单次业务请求验证，并确认 Docker 健康状态恢复正常。
- Kavita 的迁移进度日志使用了 `Fatal` 等级，但文字明确写明不是错误；迁移已完成，不能仅凭该单词判定启动失败。

版本来源包括各项目官方发布页；Seerr 使用 [官方版本标签约定](https://github.com/seerr-team/seerr/blob/develop/docs/getting-started/docker.mdx)，Kavita 使用 [官方稳定镜像](https://wiki.kavitareader.com/installation/docker/dockerhub/)，并以运行日志确认实际版本。
