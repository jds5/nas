# 备份盘休眠监控记录（sda / sdb）

> **迁移说明（2026-09-10）**：来自 Homeland；原文中的“本轮”“已完成”和版本信息保留原记录日期，本次未复验现网。

> 本文档定位：休眠启用后，**多日监控两块备份盘的启停/唤醒情况**，以防意料之外的反复唤醒（thrashing）。
> 配套：[备份盘休眠配置.md](备份盘休眠配置.md)（方案与能力实测）、[运维记录.md](运维记录.md)。
> 范围仅 `sda`(secondary-mirror) / `sdb`(critical-mirror)；16T `sdc`(pool-main) 不监控、不休眠。

## 一、读取磁盘信息会不会唤醒盘？（关键）

| 命令 | 是否唤醒休眠盘 | 说明 |
| --- | --- | --- |
| `hdparm -C /dev/sdX` | **否** | ATA `CHECK_POWER_MODE`，非介质命令，专为查电源状态而不唤醒 |
| `smartctl -n standby -A /dev/sdX` | **否** | 盘在 standby 时直接跳过（exit 2），不读 |
| `smartctl -A /dev/sdX`（普通） | **是 ⚠️** | 发起 SMART 读，会拉起盘片 —— **会污染唤醒计数，监控时禁用** |

要点：`Start_Stop_Count` 等计数**休眠期间不变**，所以盘睡着时跳过读 SMART 不丢信息。监控脚本一律先用 `hdparm -C` 查态、`smartctl -n standby` 读计数，**全程零唤醒**。

## 二、监控机制（已部署在 NAS）

| 组件 | 路径（NAS，`/opt/nas/scripts/`，随 nas-config git-backup 版本化） | 作用 |
| --- | --- | --- |
| 转换记录器 | `disk-power-monitor.sh` | cron 每分钟跑，用 `hdparm -C`（不唤醒）采样，**仅在状态变化时**追加一行 |
| 转换日志 | `disk-power.log` | 形如 `2026-06-15 21:11:31  sdb  active -> standby` |
| 状态文件 | `.disk-power.state` | 记录上次状态用于比对 |
| 报告脚本 | `disk-power-report.sh` | 一条命令出报告：当前态 + 计数（非侵入）+ 累计 spindown/spinup 次数 + 最近转换 |

cron：`* * * * * /opt/nas/scripts/disk-power-monitor.sh`（yao 用户级，调用 `sudo -n hdparm -C`）。
> `hdparm -C` 无数据传输 → 不增加 `/proc/diskstats` 计数 → **不会重置 hd-idle 空闲计时器**，监控与休眠互不干扰。

## 三、每隔一天的检查办法

在 NAS 上或本机 SSH 跑（任选其一）：

```bash
# 在 NAS 上
/opt/nas/scripts/disk-power-report.sh

# 或本机一条命令
ssh yao@192.168.50.33 /opt/nas/scripts/disk-power-report.sh
```

把每次 `Start_Stop_Count` 填进下方《监控台账》，与上一次做差（delta）。

### 判读标准（休眠启用后的预期）

晨间排程：sdb 在 02:00/06:00/07:00 被访问、sda 仅 06:00。配 20 分钟空闲休眠后，预期每天 spindown：

| 盘 | 预期 spindown/天 | 2 天预期 Start_Stop delta |
| --- | --- | --- |
| sda (secondary-mirror) | ~1 | ~2 |
| sdb (critical-mirror) | ~2–3 | ~4–6 |

- **正常**：delta 接近上表。
- **异常（反复唤醒）**：delta 远超预期（如 2 天几十上百次）→ 有进程在频繁戳盘。用 `disk-power.log` 看转换时间规律 + 当时 `restic*.log`/容器日志定位元凶。
- 监控建议持续 **3–5 天**确认稳定后即可放心。

## 六、首轮 26 小时监控结论（重要：休眠几乎未生效）⚠️

**数据（2026-06-15 21:10 → 06-16 23:48，~26.6h）**

| 盘 | Start_Stop Δ | 真实 spindown（剔除验证） | 睡眠总时长（估） | 结论 |
| --- | --- | --- | --- | --- |
| sda | +3 | 2 次（21:54、06:22） | ~52 分钟 | 约 **97% 时间在转** |
| sdb | +5 | 4 次（21:54、02:22、06:21、07:21） | ~83 分钟 | 约 **95% 时间在转** |

转换日志显示：两盘晨间（凌晨备份链前后）有几次短睡（12–36 分钟即被唤醒），**自 06-16 07:39 起连续运转 16–17 小时未再休眠**。省电目标基本落空。

**根因（已实测定位）**

1. **diskstats 冻结但盘不睡**：06-17 00:00–00:20 实测两盘 `/proc/diskstats` 读写计数**连续 ~24 分钟零增长**（无任何块 I/O），但盘始终 `active/idle`，且日志自 07:39 后无 spindown。
2. hd-idle **只依据 `/proc/diskstats`** 判断空闲。磁盘被 **ATA/SMART passthrough（ioctl）** 唤醒时，这类访问**不计入 diskstats**。
3. 唤醒后，hd-idle 仍以为盘处于"已 spindown"状态（它没看到块 I/O 活动），于是**永不再下达 spindown** → 盘一直转，直到下次真实块 I/O 才重新计时。晨间能睡是因为紧跟真实备份 I/O。

**唤醒源验证（06-17 00:20–00:56 强制 standby 监视 36min）**

- 两盘强制 standby 后**连续保持 ~36 分钟**（io+0）→ **不存在 ~30min 高频唤醒源**（smartd `-n standby` 未频繁戳盘）。
- 00:56 两盘**同时**以 `io+0`（零块 I/O）唤醒 → **确实存在 passthrough 唤醒，但是偶发的**（非周期高频）。具体源未最终确认（smartd 仍为嫌疑之一，但非每 30min）。

**最终判定**：**主要缺陷是 hd-idle 卡死态** —— 偶发一次 passthrough 唤醒即让盘永转。唤醒源是次要因素（不频繁）。

**修复方向**

- ✅ **首选 · 方案 B：自纠正 cron 替代 hd-idle** —— 改用 cron（每 ~3min）查 `hdparm -C` **真实电源态** + diskstats 增量；盘 active 且空闲超阈值（~20min）则 `hdparm -y`。不依赖内部状态，passthrough 唤醒后能**自动复睡**；唤醒偶发，ping-pong 有限。完全在现有 hdparm 免密权限内可实现与验证。
- 备选 · 方案 A：另行定位并消除 passthrough 唤醒源（需 root 工具，如停 smartd 复测）。可作为后续把启停次数再压低的优化，非必需。

## 七、修复已部署（自纠正 cron，2026-06-17 01:0x）✅

| 组件 | 路径（NAS `/opt/nas/scripts/`） | 说明 |
| --- | --- | --- |
| 自纠正休眠脚本 | `disk-spindown.sh` | cron 每 3min；查真实电源态 + diskstats 增量，空闲 ≥1200s（20min）则 `hdparm -y`（by-id） |
| 状态文件 | `.disk-spindown.state` | 记录每盘上次 io 计数 + 空闲起始时间 |
| cron | `*/3 * * * * /opt/nas/scripts/disk-spindown.sh` | 与每分钟监控 cron 并存 |

**逻辑要点**：真实块 I/O → 重置 20min 计时（不打断备份）；passthrough 唤醒（diskstats 不变）→ 空闲计时本就未停，下个 cron 周期（≤3min）内即复睡。**故不会卡死**。

**已验证**：
- 短阈值测试（THRESH=1，连跑 2 次）→ 双盘 `standby` ✅
- **passthrough 复睡实证**：00:56 偶发 passthrough 唤醒后两盘卡在 active，本脚本检测到 active+超空闲 → 已 `hdparm -y` 复睡成功 ✅
- 部署后两盘当前为 `standby`，cron 已排程（cron 守护进程由每分钟监控日志持续产出佐证其在跑）。

**hd-idle 处置**：保留 enable 但已被 cron 取代（其卡死态无害、不冲突）。建议清理性停用（需 root，可选）：
```bash
sudo systemctl disable --now hd-idle
```

**下一步验证（明日同一办法看台账）**：预期 Δ 显著回到健康区间（sda ~1–2/天、sdb 因偶发 passthrough 唤醒可能略高但盘应大部分时间 `standby`）。重点看 `disk-power.log` 是否恢复"睡—醒—睡"的正常节奏，而非整天 active。
