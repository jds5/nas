## 开机端口绑定竞争

**根因**：`/etc/network/interfaces` 中 `enp1s0` 是 `allow-hotplug` + DHCP（dhcpcd），`ifupdown-wait-online` 未启用。10-29 开机时间线：

| 时间 | 事件 |
| --- | --- |
| 07:10:50.20 | `network-online.target` 达成 |
| 07:10:51.71 | docker.service 启动 |
| 07:10:53.76 起 | 绑定 192.168.50.33 的端口 `cannot assign requested address` |
| 07:10:53.84 | 网卡 carrier 就绪 |
| 07:11:02.76 | dhcpcd 拿到 192.168.50.33 |

Docker 比拿到 IPv4 地址早启动约 11 秒。受影响的是绑定 LAN 地址的容器：NPM（81）、Gopeed（9999）、百度网关（18888）、山路下载页（8766）、游戏原型（8767）、ddns-cf-go（9877，host 网络，靠重启策略自愈）。

**处理**：新增 `/etc/systemd/system/docker.service.d/10-wait-lan-ip.conf`，在 Docker 启动前等待 `enp1s0` 出现 `192.168.50.33/`，最多 90 秒，超时仍继续启动，不阻塞其他容器。没有改网络配置，也没有改容器端口绑定。

```ini
[Service]
ExecStartPre=/bin/sh -c 'for i in $(seq 1 90); do ip -4 -o addr show dev enp1s0 | grep -q "inet 192.168.50.33/" && exit 0; sleep 1; done; echo "192.168.50.33 not ready after 90s, starting docker anyway" >&2; exit 0'
```

选这个而不是启用 `ifupdown-wait-online`：后者对 hotplug 接口只看 `ifquery --state`，与 dhcpcd 租约是否到手没有直接对应关系；直接等地址更确定。docker.service 原有 `TimeoutStartSec=infinity`，90 秒等待不会触发超时。

**验证**：`daemon-reload` 后 `DropInPaths` 包含该文件，`ExecStartPre` 内容正确；同一命令用 `systemd-run` 在 systemd 环境运行，退出码 0；在 shell 中分别模拟地址已就绪（第 1 次即通过）和等待超时（放行、退出码 0）。只做了 `daemon-reload`，没有重启 Docker，43 个容器不受影响。**效果要到下次开机才能确认**：届时检查 Docker 日志中不再出现 `cannot assign requested address`。

**未覆盖**：网页终端开机失败的原因不同（`yao` 未登录时 `/tmp/tmux-1000` 不存在），本次未处理。

**回滚**：`sudo rm /etc/systemd/system/docker.service.d/10-wait-lan-ip.conf && sudo systemctl daemon-reload`。

## 移除未记录的 UFW 规则

用户决定三条全部移除。备份 `/home/yao/.nas-maintenance-backups/ufw-20261030/`（不入 Git）：`user.rules`、`user6.rules`（附 SHA-256）、`ufw status numbered` 与 `verbose` 原文。

```bash
sudo ufw delete allow 45678/tcp                                  # IPv4、IPv6 各一条
sudo ufw delete allow from 2408:823c:e10:15bc::/64
sudo ufw delete allow proto tcp from 2408::/16 to any port 8096
```

结果：`user.rules` 只剩 LAN 全放行、LAN SSH、两条 Samba、`192.168.50.33` 远程 SSH 共 5 条；`user6.rules` 不再有任何放行规则，`ufw6-user-input` 链为空。IPv6 入站现在全部按默认策略拒绝。

验证：六个 HTTPS 域名经 `--resolve` 指向 8443 的返回码与之前一致（302、200、307、200、302、404）；公网 `jelly.rokano.org:8443` 302、`rokano.org/home/` 200；LAN Jellyfin `8096/health` 200；当前 4 条 SSH 连接未断；之后 3 分钟内核日志没有新的 UFW 阻断。

影响：Jellyfin 经 Docker 发布在 `[::]:8096`，IPv6 走 docker-proxy 进入 INPUT 链（ip6tables `DOCKER` 链中没有 8096 的转发规则），所以原来的 `2408::/16` 规则是 IPv6 直连 Jellyfin 的唯一放行；移除后这条路径关闭，经 NPM 8443（IPv4）访问不受影响。没有程序监听 45678，删除它没有影响。

回滚：`sudo cp /home/yao/.nas-maintenance-backups/ufw-20261030/user{,6}.rules /etc/ufw/ && sudo ufw reload`。
